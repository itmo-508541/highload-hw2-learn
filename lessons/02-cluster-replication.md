# Урок 2. Кластер: брокеры, реплики, лидер, ISR, `min.insync.replicas`

После урока вы сможете:

- прочитать вывод `./hw.sh topics` и объяснить каждую колонку;
- объяснить, что гарантируют `replication factor` и `min.insync.replicas` и чем вы за них платите;
- отличить кворум контроллеров KRaft от ISR партиции;
- написать `scripts/init-topics.sh` и объяснить каждый параметр.

## 1. Реплики партиции: лидер и фолловеры

**Брокер** — сервер Kafka, который хранит партиции. У нас их три: `kafka1..3`.

**Replication factor (RF)** — сколько копий у каждой партиции. При RF=3 каждая партиция лежит на всех трёх брокерах.

Одна копия — **лидер**, остальные — **фолловеры**:

- продюсеры пишут и консьюмеры читают **только через лидера**;
- фолловеры сами забирают новые записи у лидера и дописывают к себе.

Это очень похоже на MySQL: лидер — primary, фолловер — реплика, которая тянет binlog. Разница в масштабе: лидер выбирается **для каждой партиции отдельно**. Поэтому у топика из трёх партиций лидеры обычно разнесены по разным брокерам, и нагрузка делится между ними.

## 2. ISR — реплики, которые не отстали

**ISR (in-sync replicas)** — лидер плюс фолловеры, которые успевают за ним. Если фолловер долго не догоняет лидера (по умолчанию 30 секунд, `replica.lag.time.max.ms`) или его брокер упал, лидер исключает фолловера из ISR. Когда фолловер догонит лидера, он вернётся в ISR.

Важно: **Replicas** — это где партиция должна лежать (состав не меняется при сбоях), а **Isr** — какие из этих копий сейчас актуальны.

Если лидер упал, новый лидер выбирается **только из ISR**. Это обеспечивает `unclean.leader.election.enable=false` (у нас он задан в compose). Если разрешить выбрать отставшую реплику, кластер быстрее вернётся к работе, но потеряет хвост записей, которого у неё не было. Выбор между доступностью и потерей данных — это и есть смысл этой настройки.

**High watermark.** Консьюмер видит только записи, которые уже есть у всех реплик из ISR. Иначе он мог бы прочитать запись, которая исчезнет после смены лидера.

## 3. `acks=all` и `min.insync.replicas`

Подробно про продюсер — в уроке 3. Здесь достаточно одного: при `acks=all` лидер подтверждает запись продюсеру, только когда её получили **все текущие** реплики из ISR.

Ловушка: если ISR сжался до одного лидера, то «все текущие» — это один лидер. `acks=all` тогда ничем не лучше `acks=1`: у записи одна копия.

От этого защищает **`min.insync.replicas` (minISR)** — настройка топика: «принимать запись с `acks=all`, только если в ISR не меньше N реплик». Если реплик меньше, брокер отказывает с ошибкой `NOT_ENOUGH_REPLICAS`. Писать нельзя, но читать по-прежнему можно.

Аналогия с MySQL — semi-sync репликация:

| MySQL semi-sync | Kafka |
|---|---|
| primary ждёт подтверждения от реплик | `acks=all`: лидер ждёт реплики из ISR |
| `rpl_semi_sync_master_wait_for_slave_count` | `min.insync.replicas` |
| по таймауту **переходит в асинхронный режим** и принимает запись | **отказывает в записи** |

Последняя строка — ключевое отличие: Kafka выбирает «не принять», а не «принять без гарантии».

Обратите внимание на `./hw.sh topics`: у `sandbox` сейчас `min.insync.replicas=1` — это значение по умолчанию. Его нужно задавать явно.

## 4. Контроллеры KRaft — это другое большинство

Кто решает, кто лидер партиции и кто в ISR? **Контроллеры.** Они хранят метаданные кластера: топики, конфиги, лидеров, ISR. Контроллеры договариваются по протоколу Raft: изменение метаданных принимается, когда его подтвердило **большинство** контроллеров. При трёх контроллерах большинство — два.

В нашем compose каждый узел одновременно и брокер, и контроллер (`KAFKA_PROCESS_ROLES: broker,controller`). Это важно для эксперимента 2: остановка брокера здесь — это ещё и остановка контроллера.

Не путайте два условия:

| | Что считается | Чего требует | Что ломается без него |
|---|---|---|---|
| Кворум контроллеров | живые контроллеры кластера | большинство из 3 | изменения метаданных: выборы лидеров, смена ISR |
| minISR | реплики одной партиции в ISR | не меньше N | запись с `acks=all` в эту партицию |

Колонки `Elr` и `LastKnownElr` в выводе `topics` пока пропускаем — вернёмся к ним в уроке 10.

## 5. Listeners: почему у брокера два адреса

Клиент подключается к любому брокеру из `bootstrap.servers` и получает **метаданные**: какой брокер лидирует в какой партиции и **по какому адресу** к нему ходить. Этот адрес брокер берёт из `advertised.listeners`. Потом клиент идёт напрямую к лидеру.

Поэтому брокеру нужно два адреса:

- `INTERNAL://kafka1:9092` — для контейнеров: внутри сети compose имя `kafka1` резолвится;
- `EXTERNAL://localhost:19092` — для хоста: снаружи имени `kafka1` нет, а порт проброшен на `localhost`.

Если бы брокер сообщал хосту адрес `kafka1:9092`, bootstrap прошёл бы, а дальше клиент не смог бы подключиться к лидеру.

## Практика (7–10 минут)

Работаем с топиком `sandbox` из урока 1. Перед каждым шагом **запишите предсказание**.

> Команды `hw.sh` (`topics`, `group`, `dlt`) выполняются на первом работающем брокере, поэтому останавливать можно любой. А команды `docker compose exec kafka1 ...` ниже требуют работающего `kafka1` — поэтому в практике останавливаем брокер 2.

**Шаг 1.** Посмотрите на топик:

```bash
./hw.sh topics
```

Для каждой партиции найдите Leader, Replicas, Isr. Почему лидеры разные?

**Шаг 2.** Остановите брокер 2. Предскажите: у каких партиций сменится лидер, что станет с Replicas, что — с Isr?

```bash
./hw.sh stop-broker 2
```

```bash
./hw.sh topics
```

**Шаг 3.** Запишите в `sandbox`, пока брокер 2 стоит. Консольный продюсер по умолчанию использует `acks=all`. Пройдёт ли запись?

```bash
echo 'alice:during-failure' | docker compose exec -T kafka1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka1:9092 --topic sandbox --property parse.key=true --property key.separator=:
```

**Шаг 4.** Поднимите minISR до 3 и повторите запись. Предскажите результат. Ошибка может появиться через несколько секунд: продюсер сначала повторяет попытки.

```bash
docker compose exec -T kafka1 /opt/kafka/bin/kafka-configs.sh --bootstrap-server kafka1:9092 \
  --alter --entity-type topics --entity-name sandbox --add-config min.insync.replicas=3
```

```bash
echo 'alice:must-fail' | docker compose exec -T kafka1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka1:9092 --topic sandbox --property parse.key=true --property key.separator=:
```

Проверьте, что читать при этом можно — консьюмером из урока 1.

**Шаг 5.** Верните настройку и брокер:

```bash
docker compose exec -T kafka1 /opt/kafka/bin/kafka-configs.sh --bootstrap-server kafka1:9092 \
  --alter --entity-type topics --entity-name sandbox --delete-config min.insync.replicas
```

```bash
./hw.sh start-broker 2
```

Подождите 20–30 секунд и снова выполните `./hw.sh topics`. Вернулся ли брокер 2 в Isr? Стал ли он снова лидером своей партиции? Если нет — подождите несколько минут и посмотрите ещё раз. Подсказка для объяснения: `auto.leader.rebalance.enable`.

## Вопросы для самопроверки

1. RF=3, minISR=2, ISR={1,2,3}. Продюсер с `acks=all` получил подтверждение. Сколько копий записи гарантированно существует?
2. Тот же топик, брокер 3 выпал, ISR={1,2}. Примет ли брокер запись? Сколько будет копий?
3. Почему minISR=3 при RF=3 — плохой выбор? А чем рискует minISR=1?
4. Лидер партиции упал. Фолловер на брокере 3 отставал и был исключён из ISR. Может ли он стать лидером? Чем вы платите за ответ «нет»?
5. Сколько контроллеров из трёх может упасть, чтобы кластер ещё мог выбирать новых лидеров? Почему это отдельный вопрос от minISR?
6. Утилита на хосте подключилась к `localhost:19092`. Какой адрес брокера 2 она получит в метаданных и почему важно, что это не `kafka2:9092`?

## Теперь можно писать

`scripts/init-topics.sh` — два вызова `create_topic`. Параметры `events` заданы условием. Для `events.dlt` условие задаёт только партиции и RF. Решите сами, нужен ли ему `min.insync.replicas`. Аргумент сформулируйте так: что произойдёт с ядовитым событием, если запись в DLT подтвердилась, а потом единственная копия пропала? Подсказка: в уроке 7 консьюмер закоммитит оффсет сразу после отправки в DLT.

Проверка:

```bash
./hw.sh reset
```

```bash
./hw.sh infra
```

```bash
./hw.sh topics
```

У `events` в Configs должно быть `min.insync.replicas=2`. Учебный топик `sandbox` после `reset` исчезнет — он больше не нужен.
