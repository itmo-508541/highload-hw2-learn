# Урок 1. Журнал, топик, партиция, оффсет, ключ

После урока вы сможете:

- объяснить, чем Kafka отличается от очереди и от таблицы в БД;
- предсказать, в какую партицию и в каком порядке попадут события;
- написать `message_key` и объяснить, зачем в `events` три партиции.

## 1. Kafka — это binlog, из которого сделали продукт

Вспомните репликацию MySQL:

- каждое изменение дописывается в конец binlog, старые записи не меняются;
- реплика читает binlog и **сама помнит** позицию (файл + позиция или GTID), до которой дочитала;
- мастер не удаляет запись, когда реплика её прочитала; записи удаляются по сроку (`binlog_expire_logs_seconds`);
- несколько реплик читают один binlog независимо, каждая со своей позицией.

Kafka устроена так же:

| MySQL | Kafka |
|---|---|
| binlog | **топик** — именованный журнал записей одного вида (`events`) |
| событие binlog | **запись**: ключ + значение + заголовки + время |
| позиция в binlog | **оффсет** — номер записи: 0, 1, 2, … |
| реплика со своей позицией | **консьюмер** (точнее, группа консьюмеров) со своим оффсетом |
| `binlog_expire_logs_seconds` | **retention**: удаление по времени или объёму, не по факту чтения |

Отличие от очереди (RabbitMQ на семинаре): там сообщение исчезает после подтверждения. В Kafka чтение ничего не удаляет. Поэтому разные группы читают один топик независимо, а прочитанное можно перечитать (опыт `replay` на семинаре).

## 2. Партиция: топик режут на независимые журналы

Один журнал обслуживает один сервер, а читает его по порядку один читатель. Это предел масштабирования. Поэтому топик делят на **P партиций** — P независимых журналов. У каждой партиции свои оффсеты с нуля.

Адрес записи — тройка `(topic, partition, offset)`. `events/0/17` и `events/2/17` — разные записи.

**Порядок гарантирован только внутри партиции.** Между партициями общего порядка нет.

Аналогия: таблица, шардированная по `user_id` на три сервера. Внутри шарда `AUTO_INCREMENT` упорядочен. Спросить «что было раньше: строка 17 на шарде 0 или строка 17 на шарде 2?» нельзя.

## 3. Ключ выбирает партицию

Партицию выбирает **продюсер** при отправке:

```
partition = hash(key) mod P
```

- Одинаковый ключ → всегда одна и та же партиция, пока не меняются P и функция хеша. События с одним ключом лягут в один журнал в порядке отправки и будут прочитаны в том же порядке.
- Ключа нет (`key=None`, в Kafka — `null`): клиент раскладывает записи по партициям сам. librdkafka (под капотом `confluent-kafka`) складывает их пачками в случайную партицию и время от времени её меняет (параметр `sticky.partitioning.linger.ms`). События одного пользователя окажутся в разных партициях.

Две тонкости:

1. **Пустой ключ — это не отсутствие ключа.** `b''` — настоящий ключ. Хеш у него всегда один и тот же. Подумайте, куда попадут все записи с `key=b''`.
2. **У разных клиентов разная функция хеша.** librdkafka по умолчанию использует `consistent_random` (CRC32), Java-клиент и консольные утилиты — murmur2. Поэтому в семинаре стоит `'partitioner': 'murmur2_random'` — для совместимости с Java. Если ключ `alice` отправить из консоли и из Python, он может попасть в разные партиции. В HW2 все продюсеры — один и тот же код на Python, поэтому для нас это не проблема. Но объяснить, почему не проблема, вы должны уметь.

Число партиций уменьшить нельзя. Увеличить можно, но тогда `hash mod P` для новых записей меняется: ключ «переезжает» в другую партицию, и на стыке ломается порядок. Поэтому P выбирают заранее.

## 4. Партиция — единица параллелизма

В одной группе консьюмеров каждую партицию читает ровно один участник (подробно — в уроке 4). Отсюда:

- 3 партиции → одновременно работают не больше 3 консьюмеров группы;
- четвёртый консьюмер будет простаивать, пока кто-то не уйдёт.

## 5. Что это значит для HW2

- `verify` проверяет порядок `seq` **внутри пользователя**, а не глобальный. Значит, нужен порядок внутри пользователя — и ключ, который этот порядок даёт.
- Каждый `user_id` генерирует ровно один продюсер. Если бы один `user_id` писали два продюсера, порядок их событий не был бы определён даже с ключом: кто раньше отправил, тот раньше и записан.
- В `events` 3 партиции, а консьюмеров в группе 3.

## Практика (5–7 минут)

Стенд из `highload-HW2`. Топиков `events` ещё нет — создадим учебный топик `sandbox`.

```bash
cd ~/Yandex.Practicum/ipkn/highload-HW2
./hw.sh infra     # только брокеры, kafka-init и Postgres

docker compose exec kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka1:9092 \
  --create --topic sandbox --partitions 3 --replication-factor 3
```

**Сначала запишите предсказание**, потом запускайте. Вы отправите строки `alice:1`, `bob:1`, `alice:2`, `carol:1`, `alice:3`, `bob:2`, `carol:2`, `alice:4` (до двоеточия — ключ, после — значение).

1. Будут ли все записи `alice` в одной партиции?
2. Совпадёт ли порядок вывода консьюмера с порядком ввода?
3. Какие оффсеты вы увидите: 0..7 подряд или что-то другое?

```bash
# продюсер: вводите строки по одной, в конце Ctrl+D
docker compose exec kafka1 /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka1:9092 \
  --topic sandbox --property parse.key=true --property key.separator=:

# консьюмер: печатает партицию, оффсет и ключ
docker compose exec -T kafka1 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka1:9092 \
  --topic sandbox --from-beginning --timeout-ms 5000 \
  --property print.partition=true --property print.offset=true --property print.key=true
```

Затем:

- запустите консьюмер второй раз — что изменилось? Что это говорит об удалении записей при чтении?
- отправьте несколько строк **без** `parse.key` (просто `hello1`, `hello2`, …) и посмотрите, какой ключ и какие партиции у них.

После урока топик можно не удалять: `./hw.sh reset` перед этапом 1 сотрёт всё.

## Вопросы для самопроверки

Ответьте своими словами, я проверю.

1. Продюсер отправил события `alice` с `seq` 1, 2, 3 с ключом `alice`. Может ли консьюмер прочитать их в порядке 1, 3, 2? А если ключа нет?
2. Вам сказали: «посмотри запись с оффсетом 42 в `events`». Чего не хватает, чтобы найти запись однозначно?
3. Чем «прочитать» в Kafka отличается от «прочитать» в очереди? Что происходит с записью после чтения?
4. Если создать `events` с одной партицией, что станет с порядком событий и с работой трёх консьюмеров?
5. Почему важно, что каждый `user_id` генерирует ровно один продюсер?
6. Чем `key=None` отличается от `key=b''`? Что случится с распределением по партициям во втором случае?

## Теперь можно писать

`app/producer.py` → `message_key(event, key_mode)`. Что нужно знать:

- функция должна вести себя по-разному при `KEY_MODE=user_id` и `KEY_MODE=none`; от этого зависит эксперимент 3.
